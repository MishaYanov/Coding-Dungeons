# Coding Dungeons Standalone Rust Grader Design

**Status** · Proposed design for the first Windows desktop release

## Standalone release requirement

`CodingDungeonsSetup.exe` installs all four worlds, the books, the game engine, and the complete Rust grader. On a fresh Windows 11 x64 Home or Pro PC, a standard user can install with the network disconnected, open the app, and pass a Rust challenge on the first launch. The installer carries the compiler, linker, standard library, test suites, and execution runtime. The player needs no Docker, WSL, Rust installation, Visual Studio, admin access, or first-run download. JavaScript, TypeScript, and Go use their existing guided reviews. [Desktop migration PRD](DESKTOP-MIGRATION-PRD.md)

The GM saves the draft, shows **Compiling** and **Running tests**, and lists the named cases and their results. Compilation errors point to the submitted code. Failed assertions, timeouts, cancellation, and grader faults have separate messages. After a pass, the game saves the attempt and awards eligible progress before showing the defeat animation. If the installed grader fails its integrity or sandbox checks, the GM keeps the draft and directs the player to repair the installation.

## Compiler and execution choice

Use a private Windows x64 `rustc` toolchain to compile Rust 2024 submissions to `wasm32-wasip1`. Execute the resulting WebAssembly in a bundled Wasmtime worker. WASIp1 provides enough of the Rust standard library for the installed exercises, and the Rust target ships a linker and the necessary WASI libraries for pure Rust builds. Confirm the pinned compiler, its DLLs, its WASIp1 sysroot, and the linker together on the clean-machine package. Start with the project's Rust `1.99.1` pin and ship a maintained, pinned Wasmtime release. [Rust toolchain pin](../rust-toolchain.toml) · [Rust WASIp1 target](https://doc.rust-lang.org/rustc/platform-support/wasm32-wasip1.html) · [Wasmtime release policy](https://docs.wasmtime.dev/stability-release.html)

WebAssembly lets the app bound memory and execution and give submissions only the host capabilities they need. It also avoids asking Windows to launch a newly generated unsigned `.exe` for each attempt, which can conflict with Smart App Control. Keep both the compiler and Wasmtime in restricted Windows processes. The compiler processes untrusted source too, including macros that can try to read files or environment variables at build time. [Wasmtime security](https://docs.wasmtime.dev/security.html) · [Windows Smart App Control](https://learn.microsoft.com/windows/apps/develop/smart-app-control/overview)

## Challenge compatibility

The current Rust campaign has **14 automatically graded exercises and 46 named cases**. All 14 remain graded. Use the existing assertions for 45 cases and adapt the harness that calls them. The Ironbound Scarab's curated stages keep their model checks. Its companion `split-registers` submission uses the standalone grader. [Rust exercises](../data/exercises.json) · [Encounter definitions](../lib/encounters.mjs)

Level 20's `bounded-admission` suite includes `simultaneous_callers_respect_capacity`, which starts four OS threads. The ordinary WASIp1 target cannot spawn threads. Replace that one installed case with deterministic call sequences through cloned admission handles. Verify two outstanding permits at capacity, rejected admission, a consistent snapshot, and recovery as permits drop. Include compile-time `Send` checks for the handles and permits that the original test moves across threads. Keep the original threaded test in native CI and explain in the book and GM that the installed case checks capacity and ownership across interleaved calls. It cannot expose scheduling races. Review the replacement against deliberately broken solutions before release. [Original exercise](../data/exercises.json) · [WASIp1 threading limitations](https://doc.rust-lang.org/rustc/platform-support/wasm32-wasip1.html#requirements)

## Request and grading flow

1. **Authorize and save.** Keep the existing hero, page, prompt, and exercise checks in the Node engine. Save the source before scheduling a run. The renderer supplies the exercise ID and source. The engine looks up the suite and case IDs in versioned bundled content. Keep the existing source limit and allow one active run per app instance. [Current submission route](../server.mjs)
2. **Compile the learner crate.** Start the bundled `rustc` by absolute path with fixed arguments, edition, target, sysroot, and linker configuration. Build a learner `rlib` in private scratch space without exposing the test source to this phase. Limit the inputs to a single source file and the shipped Rust standard library. Invoke `rustc` directly with a minimal environment. The submission controls neither compiler flags nor linker commands.
3. **Link the trusted harness.** Generate the harness from the bundled suite at build time. Compile the selected harness in a separate restricted job, with the learner library as input and a single bounded Wasm artifact as output. Keep the harness and compiler read-only. Run the normal shipped tests against native Rust in CI as well. The installed harness dispatches the named cases directly, since the native `rustc --test` harness expects unwinding and WASIp1 defaults to aborting on panic. [Current two-phase compilation](../infra/run-suite.sh) · [Rust test harness](https://doc.rust-lang.org/rustc/tests/index.html) · [WASIp1 target behavior](https://doc.rust-lang.org/rustc/platform-support/wasm32-wasip1.html)
4. **Execute named cases.** Start the signed Wasmtime worker in its own job. Validate the raw Wasm and its import and export shape in that worker. Compile the module there and use a fresh instance and store for each host-selected case. Count success only when the expected harness call returns normally after the assertions. Treat a trap or `proc_exit`, including exit code zero, as a failed or interrupted case. Captured stdout and stderr are diagnostics. Prototype the WASI entry point and this return contract before porting the full suite. [Wasmtime WASIp1 embedding](https://docs.wasmtime.dev/api/wasmtime_wasi/p1/index.html)
5. **Commit the result.** Correlate the broker's bounded result with the engine's attempt ID and exact suite. Only a full verified pass can grant Forge progress. Persist eligible attempts and progress atomically and make retries idempotent. Keep the source draft if the run is busy, canceled, or interrupted. A crash before the commit must leave the challenge available to retry. [Existing progression and save layer](../lib/store.mjs)

## Isolation and resource limits

A small signed Windows broker runs as the current user. Its only grading input is the attempt ID, a known exercise ID, and a size-bounded source string. Its private pipe protocol accepts no commands, arbitrary paths, or user-selected toolchains. The Electron renderer cannot reach the broker or workers directly. Native helpers sit outside Electron's archive at known resource paths.

- **Windows process boundary.** Use separate Less Privileged AppContainer (LPAC) identities for compilation and execution with zero capabilities. Grant the relevant identity access to its exact packaged binaries and attempt files. Keep hero databases, credentials, the app's loopback token, and the user's working directories outside worker access. Use explicit inherited handles and a sanitized environment. Verify the token, access rules, and job membership before letting the process run. If setup fails, close the job and return a grader fault. [Windows LPAC launch](https://learn.microsoft.com/windows/win32/secauthz/implementing-an-appcontainer) · [Windows process attributes](https://learn.microsoft.com/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute)
- **Worker lifecycle.** Put each process tree in a Windows Job Object before it executes. Disallow job breakaway and kill the job on close. Allow the expected bundled linker child in the compile job. Block child creation in the Wasmtime job. Enforce CPU, memory, process-count, and wall-clock limits. Cancellation, timeout, app exit, and broker termination close the relevant jobs. Clean attempt and private profile data, including after an interrupted run. [Windows Job Objects](https://learn.microsoft.com/windows/win32/procthread/job-objects)
- **Guest permissions.** Give Wasm bounded stdout and stderr, closed stdin, and only the arguments and WASI imports the harness needs. Use zero filesystem preopens, network access, or inherited environment. Keep thread and shared memory support disabled. Use per-case fuel, linear-memory, table, instance, and stack limits plus a host watchdog. The worker loads validated raw Wasm produced for this attempt, with no deserialization of guest-supplied native caches. [Wasmtime security](https://docs.wasmtime.dev/security.html) · [Store limits](https://docs.wasmtime.dev/api/wasmtime/struct.StoreLimitsBuilder.html) · [Execution interruption](https://docs.wasmtime.dev/examples-interrupting-wasm.html)
- **Files and diagnostics.** Put compile writes in disposable, restricted directories and check free space before creating a job. Monitor scratch growth independently of the job memory limits. Bound output and artifact sizes, reject reparse-point escapes, and strip private paths and control characters from diagnostics. Give execution only a read-only artifact or a bounded inherited read handle. Verify default AppContainer storage access during testing and include it in cleanup.

Provisional budgets are a 48 KiB source limit, 16 KiB of returned diagnostics, a 16 MiB Wasm artifact, 128 MiB of guest linear memory, 2 seconds per case, and 30 seconds for the whole attempt. Measure compiler peak memory and scratch usage to set job and disk budgets, then test termination at each limit. Keep the editor responsive while a job runs and allow the player to cancel from the GM.

These boundaries protect the PC and saves from submitted code. Scoring is local learning feedback. Anyone with control of their Windows account can inspect shipped test assets and modify their own game data.

## Installer contents and maintenance

- **Private toolchain.** Stage verified Rust distribution components in CI. Include the matching compiler and DLLs, WASIp1 standard library and sysroot, linker and support files needed for direct compilation. Include the pinned Wasmtime worker, broker, and versioned test catalog. The app resolves these files from its installed resources. Running the setup file changes neither the player's `PATH` nor a separate Rust installation. [Rust distribution options](https://forge.rust-lang.org/infra/other-installation-methods.html)
- **Verification.** Record component versions and hashes in a release manifest. Sign the first-party helpers and the final setup, and verify the publisher and executable dependencies on Windows. Include component notices and a software bill of materials covering Rust, LLVM/LLD, WASI libraries, Wasmtime, Electron, and any packaged Windows runtime dependencies. Use the notices from the actual staged components. [Rust redistribution notices](https://github.com/rust-lang/rust/blob/1.99.1/COPYRIGHT) · [Wasmtime license](https://github.com/bytecodealliance/wasmtime/blob/main/LICENSE)
- **Upgrade and repair.** Update the compiler, runtime, broker, and catalog together as a signed installer release. The GM runs a bounded bundled smoke check before accepting its first submission with a new component version. If files are missing or incompatible, reinstalling from the setup repairs the private runtime and preserves SQLite saves. Measure the complete installer. The proposed budgets with the grader are under 500 MiB for setup and under 1.5 GiB installed, excluding saves and backups.
- **Browser edition.** Keep the Docker backend for the developer/browser edition during the React migration. It is neither bundled nor selected by the installed desktop edition. Both backends keep the same engine-level attempt and progression behavior.

## Implementation and release gates

1. **Prove the offline package first.** Produce a small signed Windows test installer with the pinned compiler, WASI sysroot and linker, LPAC broker, and Wasmtime worker. Compile and grade one passing, one failing, and one malformed submission offline. Verify permission setup, worker shutdown, build diagnostics, normal return versus `proc_exit(0)`, and toolchain launch with Smart App Control enabled. Test an install path containing spaces and a Windows account name containing non-ASCII characters.
2. **Port the catalog.** Run all 14 reference solutions and starters through the packaged grader. Check the 46 expected installed cases, including the explicit Level 20 replacement. Every reference must pass. Wrong solutions and incomplete starters must fail for the expected reason. Keep native CI exercising real threads in `bounded-admission`. [Existing exercise fixtures](../test/exercises.test.mjs)
3. **Test the boundaries.** Attempt build-time reads with `include_bytes!` and `env!`. Attempt guest access to saves, profile files, loopback, external network, and subprocesses. Run a test-only Windows probe under the exact worker tokens and jobs with networking enabled to verify that Windows denies access even when the guest boundary is bypassed. Exercise infinite loops, deep recursion, allocation and output floods, excessive compiler writes, malformed module artifacts, forged output, early exit, and cancellation. Check that resource limits leave the app responsive and that no case awards progress on a timeout, spoofed result, or grader fault.
4. **Test the installed game offline.** Use clean Windows 11 Home and Pro x64 VM snapshots as a standard user. Disconnect before install and remain offline through the first successful grade, restart, upgrade, and repair. Check first-run grading, no prerequisite or network prompts, all four worlds, durable hero progress, cancellation during compilation and execution, and recovery after forced app or broker termination. Verify that repeated success does not grant extra XP and that upgrades preserve saves.

Release requires an installed build that meets all four gates. In particular, if Windows cannot enforce the compile and execution boundaries with the bundled binaries, grading remains disabled in the test build until the containment issue is resolved.
