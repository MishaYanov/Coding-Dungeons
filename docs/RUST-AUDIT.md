## GM and technical explanations

The review compared all 42 keyed multiple-choice checkpoints with the field manuals and inspected the 14 graded exercise contracts, reference implementations and named test cases. The checked topics included distinctions that affect whether a solution is correct in more than the ordinary case.

- Ownership and borrowing. An owned handle has its own lifetime, while a returned borrowed view stays tied to the backing owner. Partial moves affect which initialized fields are dropped. A safe caller can forget an ownership guard. [Destructors](https://doc.rust-lang.org/reference/destructors.html) · [Subtyping and variance](https://doc.rust-lang.org/reference/subtyping.html)
- Generic and erased interfaces. Coherence rules address overlapping implementations. A generic bound, a dyn-compatible trait and an erased return type serve different callers. An async method's `Send` promise concerns its returned future as well as any receiver bound required by the implementation. [Trait implementation coherence](https://doc.rust-lang.org/reference/items/implementations.html#trait-implementation-coherence) · [Dyn compatibility](https://doc.rust-lang.org/reference/items/traits.html#dyn-compatibility) · [Rust async trait stabilization](https://blog.rust-lang.org/2023/12/21/async-fn-rpit-in-traits/)
- Concurrency and async. A notification schedules another poll and can coalesce. Readiness and registration must agree. An acquire operation must observe the relevant release publication to supply ordering, and that ordering does not retain the allocation. Pinning constrains the pointee, with obligations for destruction and structural projections. [Future](https://doc.rust-lang.org/std/future/trait.Future.html) · [Waker](https://doc.rust-lang.org/std/task/struct.Waker.html) · [Atomic orderings](https://doc.rust-lang.org/std/sync/atomic/enum.Ordering.html) · [Pinning](https://doc.rust-lang.org/std/pin/index.html)
- Systems boundaries. A pointer's numeric address is only one part of access. Validity, provenance and allocation lifetime govern pointer operations. `MaybeUninit` storage needs separate ownership accounting. The layout of a C-compatible outer type does not establish the validity or ABI of arbitrary inner types. [Pointer module](https://doc.rust-lang.org/std/ptr/index.html) · [Undefined behavior](https://doc.rust-lang.org/reference/behavior-considered-undefined.html) · [MaybeUninit](https://doc.rust-lang.org/std/mem/union.MaybeUninit.html) · [Type layout](https://doc.rust-lang.org/reference/type-layout.html) · [Rustonomicon FFI](https://doc.rust-lang.org/nomicon/ffi.html)
- Project configuration. Feature unification depends on the resolved dependency instance and the resolver's rules. Additive features keep combinations meaningful. [Cargo feature unification](https://doc.rust-lang.org/cargo/reference/features.html#feature-unification)

## Verification results

- The Rust 1.99.1 compiler accepted 144 listings and rejected all 12 deliberate failures for their expected diagnostics. The 122 complete examples with `main` ran on Windows x64. A separate probe exercised lifetime shortening during unsizing, raw DST layout, owned `Box` and `Vec` pointer round trips, and C-variadic definitions.
- All 46 native assertions across 14 graded exercises passed on their reference solutions. All 14 unfinished starters failed their suites, and five invalid callers failed to compile. Mocked grader tests exercise resource flags, verdict parsing, concurrency admission, and cleanup.
- The 36 passing Node checks and four Chromium tests cover HTTP input and asset serving, SQLite migration and hero isolation, the complete reader corpus, and browser focus, navigation, and saves. The audit fixed an outgoing hero's last-page write and an old response clearing a newer draft. The grader parser now separates native outcomes from captured learner output that happens to resemble those outcomes.
- The rebuilt PDF has 559 pages, all 326 named anchors in their previous locations, 171 verified form fields, and no layout flags. In Level 37, one listing moved from page 429 to 428, and training questions 2 and 3 moved from page 436 to 435. The reader data follows the revised print layout.

## Reproduce the checks

Run `npm test`, `npm run test:browser`, and `npm run test:book` for the app, browser, and trusted Rust listing suites. The book checks require Python, Rust 1.99.1 or later, and a host linker for executable examples. Check `rustc --version` first to reproduce the reviewed toolchain. The app's learner submissions run through the separate Docker grader.

The Level 25 regression runs Listing 25.2 against an Arc-backed waker whose destructor probes the mutex. It checks that replacing a registration runs that destructor with the mutex released, wakes the current registration and delivers a value published before polling. Both cases passed on Rust 1.99.1. The original version failed the destructor check when compiled against the same fixture.

The compiler check covers standalone Rust listings and deliberately rejected witnesses. Sketches describe partial programs, configurations or architectural interfaces. Native executions exercise particular inputs on the host target. They do not establish all schedules, soundness for arbitrary clients or foreign ABI behavior on untested targets.

Live Docker grading was skipped during this audit because the local Linux engine was unavailable. The shipped image tag is `rust:1.99.1-slim-bookworm`. The grader supports local practice. Learner code and the native test harness share a process, so Forge marks are self-assessment records. [Official Rust image](https://hub.docker.com/_/rust)
