# Rebuild the Ferrum books

The Windows rebuild uses Python 3, Poppler's `pdftoppm` on `PATH`, and the Georgia, Calibri, and Consolas fonts from Windows. The reader uses the existing PDFs and page images directly.

Run these commands from the project folder to rebuild JavaScript, TypeScript, C#, and Go.

```powershell
python -m pip install -r requirements-book.txt
python build-worlds.py
```

Edit `data/worlds/<world>/source.json` to change a campaign. Pass `javascript`, `typescript`, `csharp`, or `go` to rebuild only that world. The script generates its campaign and page data beside the source, then writes the PDF, WebP pages, and field kit under `public/book/<world>`. Each PDF also embeds its field kit.

The Rust rebuild also requires Node.js 24 or newer, Rust 1.99.1 and 1.100.0, and a host linker. The project and packaged runner retain the 1.99.1 baseline; the book is also validated on 1.100.0. The experimental mobile compiler is a separate compatibility target.

```powershell
python -m pip install -r requirements-book.txt
rustup toolchain install 1.99.1 1.100.0 --profile minimal
python work/scripts/build_campaign.py
python work/scripts/check_book_toolchains.py
python work/scripts/package_examples.py
python work/scripts/package_campaign.py
python work/scripts/verify_campaign.py
python work/scripts/qa_campaign_layout.py final
python build-book.py
npm test
```

The technical manuscript lives in `work/manuscript`. Quest and route material live in `work/gamebook`. Edit multiple-choice checkpoint text in `data/checkpoints.json`. The exercise authoring script `work/ferrum-exercise-author.py` generates `data/exercises.json` with starters, reference implementations and tests. `build-book.py` maps these inputs onto the rebuilt PDF and regenerates `data/campaign.json`, `data/pages.json`, and `public/book`.

The packaging scripts build the field kit from the checked listings and attach it to the PDF. The PDF checks validate the attachment, navigation targets, listing labels, and fillable progress fields. The layout check flags empty pages and out-of-bounds text, renders the pages, and creates contact sheets in `work/qa/campaign/final`. Review edited pages there before publishing an updated reader. Keep prompt IDs and page anchors stable when editing a released campaign, since saved answers use both.

Run `python verify-worlds.py` against the finished reader. It checks every PDF page, page image, book link, and prompt binding, and compares the attached field kits with the downloaded copies. Pass a world ID to check just that world.

After `npm ci`, run `python verify-worlds.py typescript --check-typescript` to compile the TypeScript kit examples with the documented command. The CI workflow runs this check.

With the .NET 10 SDK installed, run `python verify-worlds.py csharp --check-csharp`. This runs each authored example and starter from the exported kit as an independent file-based app and compares the example’s final output line. Set `DUNGEONS_DOTNET` to a private SDK's `dotnet` executable to check without adding it to `PATH`. CI uses SDK 10.0.404.
After publishing a new PDF into `public/book`, run `python work/scripts/build-reader-text.py <world>` to regenerate the text edition. It keeps the published pagination and extracts the text and code from the PDF generated by the manuscript build. Drop the world argument to rebuild all five. `python work/scripts/build-reader-text.py --check` verifies that the packaged text and PDF revision match.
