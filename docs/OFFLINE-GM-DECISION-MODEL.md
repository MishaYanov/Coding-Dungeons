# Coding Dungeons Offline GM Decision Model

Build the first GM evaluator as a small decision table in the local game engine. Each eligible question has a rubric written with the book. The GM checks the submitted answer for specific ideas, adds the points it can verify, and selects feedback from an authored map. The player can ask to see the example answer. The GM can also ask for clarification when it cannot tell what the player meant. This design fits the standalone Windows installer and requires no model download or network access. [Desktop migration PRD](DESKTOP-MIGRATION-PRD.md)

## Questions the GM can assess

The shipped books contain 448 text cards, of which 271 are field notes. The other 177 include factual questions, experiments, and design discussions. Rust already has 104 training prompts with written example answers. Those give the pilot a head start, but each still needs a rubric with acceptable alternatives and common misconceptions. JavaScript, TypeScript, and Go have 14 non-note text cards each. Start with short answers where a subject expert can agree on the points. Let the book mark a card as gradable only after its rubric passes review. [Rust page catalog](../data/pages.json) · [JavaScript](../data/worlds/javascript/pages.json) · [TypeScript](../data/worlds/typescript/pages.json) · [Go](../data/worlds/go/pages.json)

The app already has structured question text, prompt IDs, and feedback. Read that data directly. If players later import questions from an open-source question bank, accept a local content pack with provenance, license, and reviewed rubrics. A question without a rubric can still be shown with its authored guidance. A question or answer is always treated as text data.

## What the research supports

| Evidence | Implication for the GM |
| --- | --- |
| Nielsen and colleagues labeled individual facts in short answers. Human annotators agreed on 86.2% of tutor labels in that study, with κ = .728. The SemEval student-response task distinguishes incomplete answers from contradictions and irrelevant responses. [Facet annotation](https://aclanthology.org/L08-1166/) · [SemEval 2013](https://aclanthology.org/S13-2045/) | Give credit for individual ideas and use different feedback when an idea is missing, unclear, or contradicted. Review labels with a second person. |
| Desmarais and colleagues reported a correlation of **0.482** between raw MiniLM similarity to reference answers and human scores on the Mohler computer science data. Their stronger result used a different embedding model and regression trained on graded responses per question. [EDM 2025 study, Tables 1 and 2](https://educationaldatamining.org/EDM2025/proceedings/2025.EDM.short-papers.124/index.html) | A cosine of 0.60 gives no basis for awarding 60 points. Embeddings can help locate possible paraphrases for a specific claim. |
| SemAntoNeg probes negation and antonyms. HANS found that trained entailment models can still rely on misleading word overlap or sentence structure. Ding and colleagues showed that shuffled student answers can fool content scorers. [SemAntoNeg](https://aclanthology.org/2022.blackboxnlp-1.20/) · [HANS](https://aclanthology.org/P19-1334/) · [Adversarial content scoring](https://aclanthology.org/2020.coling-main.76/) | Test near-miss answers, reversed relationships, and keyword stuffing. Even a local model trained to spot contradictions needs testing on the game’s vocabulary. |
| The 2026 BEA shared task on German short answers found that systems that explicitly applied rubrics performed well and that unseen questions remained difficult. A separate 2026 study of two biology items found that several grading models agreed less with expert scores on partially correct answers. [BEA 2026 shared task](https://aclanthology.org/2026.bea-1.85/) · [Partial-credit study](https://aclanthology.org/2026.bea-1.29/) | Evaluate each authored question on unseen responses. Measure mid-range scoring separately because that is where the GM needs to give the most useful feedback. |

One check with wording adapted from a real Rust question illustrates the issue. Removing `not` from “Preallocating storage does not let refresh take an exclusive borrow while the entry remains shared” reverses the claim while retaining 14 of 15 unique words. Measured token-set similarity was **93.3%**. Swapping the subjects in “The queue owns the fields. The parser borrows the buffer.” gives **100%** token-set similarity even though both roles change. These are counterexamples to using word overlap as a score. The scorer still needs a local validation set.

## The scoring decision

Author a versioned rubric per world and stable question ID. Store the prompt revision, points for each distinct claim, accepted ways to express the claim, examples of contradictions, one short hint per concept, and the authored answer. Use whole-number weights that add to 100 so rounding cannot turn a partial answer into full credit. Allow equivalent proof paths to earn the same points when the question permits them. Give an idea credit once, even if the player repeats it or names several synonyms. Validate the rubric at book build time and reject missing question IDs, invalid weights, and missing answer text. Use the ordered table as the decision model. The engine can express it with ordinary data and functions. [OMG Decision Model and Notation](https://www.omg.org/spec/DMN/1.5/About-DMN)

On submit, match short clauses against the current rubric. Keep technical symbols and distinctions such as `&mut`, `==`, `===`, `Send`, and `Sync`. Inspect who acts on what and under which condition. For example, “a borrow can end at its last use” and “a borrow can end before its last use” have different consequences. A match must support the relationship, not merely name both terms. Mark each claim as supported, contradicted, not detected, or unclear. For cases the rules cannot resolve, such as an ambiguous `not`, a quotation, or a self-correction, ask a focused follow-up when the ambiguity affects the score.

Calculate the percentage from the **sum of supported rubric points divided by total available points**. Show “60% of rubric points verified” so the player knows how to read it. A missing match may mean the player left out a concept or expressed it in an unfamiliar way. Suppress the percentage when there is no reliable evidence to score or when key evidence conflicts. A known critical misconception gets its own correction and takes precedence over score-based praise. Keep thresholds in one ordered table and select the first applicable row.

| Condition | Example GM response |
| --- | --- |
| Clearly stated critical misconception | “Preallocation changes capacity. `refresh` still requires exclusive access. Want a hint or the example answer?” |
| No reliable evidence, or unclear or conflicting evidence | “I can’t tell when you think the first borrow ends. Does the code use the returned entry after `refresh`?” |
| 1–39% verified | “You’ve got a starting point. Want a hint for the next part?” |
| 40–79% verified | “You got part of it. Want a hint for the rest, or to see my answer?” |
| 80–99% verified | “Most of your reasoning checks out. Try adding why the last case behaves differently.” |
| 100% verified | “You covered every part of this question. Compare your approach with my example?” |

These thresholds govern feedback tone. An author can specify a more useful hint for a given missing claim. The **Show example answer** button reveals the stored text on request. Players can try again before or after seeing it.

## A real 60 percent answer

On Rust page 25, `training-1-3` asks why a call to `current(&self) -> &Entry` can precede `refresh(&mut self)` and why reserving capacity generally fails to make a later use of the entry legal. A proposed rubric gives **20 points** for the shared borrow being able to end at its last use, **40** for recognizing that later use keeps the borrow live across `refresh`, and **40** for explaining that preallocation leaves the exclusive-access contract in place. [Book question](../data/pages.json) · [Rust Book on borrowing](https://doc.rust-lang.org/book/ch04-02-references-and-borrowing.html)

> The shared borrow may end after the last use of the entry. Using the entry after `refresh` would make that borrow overlap the mutable one.

The GM can verify 60 points and reply “You got the last-use rule and the overlap. Can you explain why more capacity still doesn’t let `refresh` borrow exclusively? Want to see my answer?” The same rubric routes “Preallocation makes both borrows legal” to the misconception response even if the rest of the answer matches the example. A player who writes “the shared borrow stays alive until the final read” needs credit if that is an approved equivalent. That is a useful held-out paraphrase if the initial matcher misses it.

## App integration and offline limits

- **Engine.** Use a pure JavaScript or TypeScript scorer in the existing local Node engine. Score on submission, with a bounded amount of text and work per attempt. Keep rubric rules as validated data. Use bounded token patterns with scoped negation and approved aliases. A rubric controls which claims can earn points. It never supplies executable code. The scorer has no HTTP client, API credentials, web tools, or model loader. [Existing answer route](../server.mjs)
- **Game and saves.** Keep choices on the existing Boolean path and code on its grader or guided review path. For assessed text, store the submitted response and its assessment in one SQLite transaction keyed to the same hero and prompt. Include rubric revision, points, claim statuses, and feedback IDs. Add a separate structured assessment field or table because `responses.correct` is a Boolean. On reload, return the saved assessment instead of applying the existing generic text feedback. Bind responses to the submitted text and active hero so a late response cannot appear under another draft. Old answers can be reassessed on request. In the pilot, a GM result is coaching and does not grant Forge completion or XP. [Store and migrations](../lib/store.mjs) · [GM prompt UI](../src/renderer/guide.jsx)
- **Memory.** Interpret the **2 GB target** as 2,000,000,000 bytes across the app and its workers. Microsoft specifies at least **4 GB installed RAM** for Windows 11. Test on a clean Windows 11 x64 VM with 4 GB, two vCPUs, and SSD-backed storage. Measure the peak time-aligned sum of private resident memory and track private commit separately. Include Chromium, the Node engine, Canvas and book pages, and Rust compiler and Wasmtime jobs. The Rust guest memory limit covers only one part of that total. Initial acceptance targets are a p95 under 50 ms for scoring, a p95 under 200 ms for click-to-feedback, and under 25 MiB incremental private resident RAM for the rules-only GM. [Windows 11 requirements](https://www.microsoft.com/en-us/windows/windows-11-specifications) · [Windows memory counters](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex2) · [Rust grader design](STANDALONE-RUST-GRADER-DESIGN.md)
- **Privacy.** Keep rubrics, answers, and results on disk in the app. Load every scoring asset by local path. Test that fresh offline installation, scoring, restart, and answer reveal all work. Also trace DNS and network activity during those actions on a connected test machine to check for outbound requests.

## When a small model would help

If the pilot finds a recurring problem with valid paraphrases, compare the rules with a small English sentence encoder that ranks candidate clauses. The quantized all-MiniLM-L6-v2 ONNX artifact is listed at about **23 MB on disk**. That excludes the tokenizer, runtime, and RAM during inference. A match from the encoder can prioritize a claim for checking or help select a follow-up. The same evidence and contradiction rules still decide points. [Model card](https://huggingface.co/sentence-transformers/all-MiniLM-L6-v2) · [Quantized artifact](https://huggingface.co/Xenova/all-MiniLM-L6-v2/blob/main/onnx/model_quantized.onnx)

Keep this experiment outside the default install until it helps on held-out answers. If it does, bundle pinned assets, use one lazy CPU session with limited threads, and precompute the rubric vectors. Disable remote model and runtime loading. Check the runtime’s Windows dependencies on a clean offline install. A native ONNX Runtime build may require the Visual C++ runtime. An entailment classifier is a separate experiment if ranking alone cannot resolve the important misses. A generative model adds runtime and validation work when the GM already has authored feedback and example answers. [ONNX Runtime requirements](https://onnxruntime.ai/docs/install/#requirements) · [Transformers.js local assets](https://huggingface.co/docs/transformers.js/en/custom_usage)

## Validation before enabling scores

1. **Write a pilot rubric set.** Start with 16 eligible questions, ideally four per world. Assemble around 400 short responses with correct variants, partial answers, genuine misconceptions, and uncertain phrasing. Have two subject reviewers independently label the claims, points, and preferred feedback. Review disagreements and fix vague rubric language before scoring.
2. **Lock the holdout.** Keep answer variants from the same paraphrase family in the same split. Hold back a representative set of mid-range responses and at least 150 critical negative cases. Include negation, swapped roles, valid alternatives, non-native English, identifiers, contradictory or self-corrected answers, word salads, and text asking the GM to award points. Compare a token-overlap baseline, rubric rules, and any optional model on the same holdout. Measure new-question transfer separately if it becomes a product requirement. [SemEval evaluation splits](https://aclanthology.org/S13-2045.pdf)
3. **Set gates.** As initial release criteria, aim for at least 95% precision on awarded claims, at least 75% scored coverage on in-scope answers, and mean absolute score error at or below 10 percentage points among answers that receive scores. Require zero praise or high-credit verdicts on the critical-misconception holdout. Report the counts, coverage, claim recall, and errors by world and score range. Also review feedback wording for answers where the GM abstains. Zero failures in 150 independent cases would still leave a one-sided 95% upper bound near 2%. Variants from the same question can be correlated, so report that limitation.
4. **Measure the packaged game.** Collect cold and warm latency, peak memory, and responsiveness with a book open, a creature animating, and Rust grading active. Repeat submissions, switch heroes and worlds, and check that the correct result survives restart. Run both connected network monitoring and disconnected installation tests. Use the measured results to decide which question rubrics to enable.

## Recommendation after testing the bundled model

The current Qwen3-0.6B Q8_0 build is useful for coaching, but its score is sensitive to wording. In an eight-answer spot check across the four worlds, two equivalent correct JavaScript answers scored 65 and 100. A correct Rust paraphrase scored 80, and a correct Go paraphrase received no score. This is a diagnostic sample, not a measured accuracy rate. The game keeps the percentage as an estimate and never uses it to remove HP or earn combat progression.

1. Build and label the holdout above before changing the default model. Include pairs that differ only by sentence breaks, synonyms, or negation. Track scores, abstention, false full credit, and consistency between equivalent answers.
2. Keep Qwen3-0.6B Q8_0 (639 MB on disk) as the baseline. Compare it offline with Qwen3-1.7B Q4_K_M (about 1.28 GB on disk) using the same prompts, scoring rules, and answers. A weights file size does not measure peak RAM. Only replace the baseline if the larger model improves held-out results and meets the installed app's total 2 GB memory target and latency targets. [Current model files](https://huggingface.co/Qwen/Qwen3-0.6B-GGUF/tree/main) · [Larger candidate](https://huggingface.co/ggml-org/Qwen3-1.7B-GGUF/tree/main)
3. Fix any rubric or evidence rules that reject valid equivalents before training. Try [LoRA fine-tuning](https://arxiv.org/abs/2106.09685) only if the benchmark still shows recurring model errors and there are enough reviewed training labels. Train separately from the app. Keep the held-out answer families out of training and ship only the validated, pinned weights.
