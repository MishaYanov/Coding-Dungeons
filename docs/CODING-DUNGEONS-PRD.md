# Coding Dungeons Standalone App PRD

**Status** · Local implementation preview. Clean Windows, full memory, and model accuracy release gates remain open.

Coding Dungeons is an offline Windows game for learning JavaScript, TypeScript, Rust, and Go. The player installs it once, chooses a world and hero, reads the book on the left, and plays through the GM on the right. In **Code Workbench**, submitting code that passes every required test defeats the monster. For written questions, a bundled LLM compares the submitted answer with the authored answer and rubric. The GM explains the result in character. **Hard Mode** locks coaching and spoilers while preserving evaluation and test feedback.

This PRD sets the release scope. The earlier desktop, Rust sandbox, and GM research notes provide implementation detail and evidence. [Desktop migration notes](DESKTOP-MIGRATION-PRD.md) · [Rust sandbox design](STANDALONE-RUST-GRADER-DESIGN.md) · [GM research](OFFLINE-GM-DECISION-MODEL.md)

## Product scope

| Requirement | First release |
| --- | --- |
| Platform and installer | Windows 11 Home and Pro x64. A single `CodingDungeonsSetup.exe` installs `Coding Dungeons.exe` per user, with a Start menu shortcut. A standard user can install while disconnected and start playing immediately. |
| Packaged content | Four worlds, 84 levels, 718 page images, PDFs and field kits, game assets, SQLite engine, test suites, language runtimes, and the local GM model. |
| Player accounts | Create or load a local hero per world. Show what each learning path covers, who it suits, and where it starts. The character sheet shows levels, XP, skills, and difficulty badges. |
| Reader | Book on the left and GM on the right, with a narrow-window layout, map, chapter jumps, and offline PDF and field-kit exports. **A/D** and arrow keys turn pages outside the editor, text fields, menus, and dialogs. |
| Standalone operation | The installer includes all components for play and grading. Players need no separate Node, Rust, Go, Docker, WSL, account, or model download. Developer builds can still use the existing browser entry point during migration. |
| Memory | Target a **2 GB peak footprint for the whole app and workers**. Windows 11 itself specifies at least **4 GB of installed RAM**. Benchmark the installed app on a 4 GB machine. [Windows requirements](https://www.microsoft.com/en-us/windows/windows-11-specifications) |

The release covers local Windows play, manual signed upgrades, and local save transfer. The learning game uses local badges and personal records. Mobile ports, cloud accounts, and online rankings are later products.

## Player flow and progression

1. Launch from Start and see all four worlds in order, with JavaScript first. Pick a world, read the path explanations, then create or resume a hero. Resume the chosen hero's last page and restore drafts.
2. Read the page and use the matching GM panel. The panel presents a choice question, a rubric-based written question, Code Workbench, a special encounter, or a notebook. Preserve the Ironbound Scarab and Stolen Signal and their saved stages. Keep field notes and exploratory work available as drafts.
3. In a coding encounter, choose Guided or Hard, edit the starter code, run examples, and submit. The creature has a ward for each required group, such as Basics, Edge Cases, or Type Contract. Show text and accessible status alongside the Canvas animation. Let players retry immediately from a retained draft.
4. A full verified submission updates the attempt, challenge clear, Forge and any XP in one transaction. After the game receives the saved result, play the defeat animation and update the character sheet. On a reopened page, show the defeated state. A retry or duplicate result cannot award the same progress twice.

The Diamond Goblin is an optional ambush in every world. Until a hero discovers it, place one diamond at a stable random location on one page in each block of eight pages. Clicking the diamond opens the encounter in the GM and saves discovery. Require a full code suite pass followed by a correct multiple-choice answer. The win awards three diamonds once, shown on the character sheet, and a healing potion in One Life. The encounter does not change book quest completion. Failed graded stages cost 5 HP in One Life; examples and runner outages leave HP unchanged.

## Code Workbench

The Workbench shows the contract, starter code, editor, examples, and results. **Run Examples** executes public cases or a bounded custom input for challenges with a typed input format. It can show expected and actual values, structured diffs, and limited output. **Submit** runs the published required suite, including sealed cases. A pass on examples, a strong written answer, or a partial test pass leaves the monster standing. This uses the familiar Run and Submit distinction from coding practice tools. [LeetCode practice flow](https://support.leetcode.com/hc/en-us/articles/360012016874-Start-your-Coding-Practice)

### Challenge catalog

Every card marked as a coding challenge needs a versioned suite. The current books contain 75 boss code cards and five additional Rust drills with suites. These are **80 initial encounter slots**. Only 14 already have suites, all in Rust, so 66 initial slots need authored suites or a testable slice of a larger project. Inventory the remaining code cards as scratchpads, review activities, or additional challenges with suites. When a project also asks for a diagram, design rationale, or release plan, the suite tests its executable component and the GM guides the review of the other work. Update the book copy and generated pages when a guided code review becomes a graded encounter. [Current Rust suites](../data/exercises.json) · [World book generator](../build-worlds.py)

Each challenge carries a stable world and challenge ID, content and suite revisions, language and runtime version, entry point and allowed input, starter and reference solutions, authored hints, budgets, and a reward rule. Each case carries a stable ID, group, visibility, and an expected outcome. Use typed inputs and outputs where they capture the contract. Use trusted language-specific fixtures for identity, mutation, async ordering, compile-time constraints, or concurrency. A typical suite has a public example plus sealed edge cases. Fixed seeds and controlled inputs make failures reproducible. Sealed cases return group outcomes and counts. Keep their inputs, assertions, and guest output out of normal feedback. The player owns the offline installation, so local packaged assets are inspectable.

| Encounter | What the suite must prove |
| --- | --- |
| JavaScript Level 12 · Stolen Signal companion | `makeLatest` publishes the latest result or failure. Controlled promises test stale success, stale rejection, repeat queries with distinct requests, and a synchronous throw. |
| TypeScript Level 13 · Dock ID | The runtime parser validates the documented ID format. Compile-time fixtures reject an unbranded string where a `DockId` is required. |
| Rust Level 3 · Ironbound Scarab companion | `two_mut` keeps the requested order, works with move-only values, and rejects repeated or invalid indices. The existing forward-order case is a good public example. |
| Go Level 4 · Tagged slice | `withTag` returns the right sequence with independent storage. Test spare capacity and mutate the returned slice to check that the caller's data stays intact. |

A design check ran six `makeLatest` cases against trusted JavaScript. The reference passed all six. An unguarded version passed two, a query-keyed version passed five, and a version that swallowed failures passed four. A separate trusted Go WASI reactor probe compiled on Windows and returned the expected results through a goroutine and channel. Those checks exercise the proposed fixtures and ABI. The packaged security and runtime gates below still apply. [JavaScript exercise contract](../data/worlds/javascript/source.json) · [Go WASI reactors](https://go.dev/blog/wasmexport)

### Runtime results and game rules

Show **Preparing**, **Compiling or type checking** where applicable, **Running tests**, and the final verdict. Distinguish wrong answer, compiler or type error, runtime failure, timeout, resource limit, cancellation, and engine fault. Each case has a bounded deadline and a fresh execution state unless the exercise explicitly tests state across calls. Measure each case with the host's monotonic clock. Display total test runtime and public case timings separately from compile time. Aggregate sealed timings to avoid exposing the individual fixtures. The run's timing is for this machine and suite revision. Base wins and XP depend on correctness. A future speed trial can use a defined workload and publish its own rules. [Node monotonic timer](https://nodejs.org/api/process.html#processhrtimebigint)

## Hard Mode and suggestions

Choose difficulty per encounter before starting. **Guided Mode** offers a requested nudge, a more direct approach, and an optional code snippet. Hints are authored by challenge and can be selected using safe case categories or compiler diagnostic codes. Show a snippet preview with **Apply** and undo. Semantic autocomplete can be piloted later as a local editor feature using those same suggestions. Code suggestions do not need a second model or free-form generation. [CodeMirror completion sources](https://codemirror.net/examples/autocompletion/)

**Hard Mode** locks hints, solution snippets, semantic completions, debrief spoilers, and the written answer reveal until the relevant encounter clears or the player switches to Guided. Keep public examples, normal compiler diagnostics, the score, and test status. The GM can evaluate a submitted answer in either mode. In an active Hard attempt, show the score and a brief verdict without revealing missing rubric claims or the solution. A written question can unlock its debrief at full rubric credit. Only a passing code submission can defeat a coding creature. Use the same tests and rewards for standard progression. Add a **Hard clear** badge for an eligible unaided win.

Enforce difficulty in the engine as well as the editor. Gate the existing hint and debrief routes, GM answer reveal, and any completion provider. Scope cached replies to the hero, challenge revision, and attempt. Discard pending guidance when the mode, hero, or prompt changes. Switching to Guided keeps the draft and ordinary rewards. Record prior aid disclosure for the same challenge and equivalent revisions so switching back cannot restore badge eligibility. Players can try a fresh variant for a new unaided badge. [Existing reveal route](../server.mjs) · [Current prompt and hint UI](../src/renderer/guide.jsx)

## Offline LLM Game Master

The model's job is to compare the player's submitted **written answer** with the question, the book's correct answer, and its versioned rubric. Multiple-choice grading uses the authored key. Code Workbench uses the executable test suite. Give the model the current lesson and response only. The player sees GM feedback assembled from authored text, with an explicit button to reveal the predefined answer when allowed.

1. **Author the rubric.** Give each distinct claim a weight. Use whole-number weights totaling 100, correct alternatives, known misconceptions, and approved feedback and example answers. Only reviewed questions enable scoring. Start with 16 short questions across the four worlds. Rust already has 104 training prompts with authored answers, which give the pilot a starting point. Free-form design debates and field notes stay available as unscored activities. [Question inventory and validation research](OFFLINE-GM-DECISION-MODEL.md)
2. **Ask the local model for evidence.** On submit, label clauses in the answer and pass them as bounded text data with the question and answer key. Require one status per criterion, such as supported, contradicted, not detected, or unclear, with a matching clause ID where evidence is claimed. A grammar constrains the response to a small schema. The model gets no tools, browsing, chat history, or access to other saves. [llama.cpp constrained output](https://github.com/ggml-org/llama.cpp/blob/master/grammars/README.md)
3. **Validate and score in the engine.** Check all IDs, evidence references, required fields, and conflict rules. A recognized critical misconception takes precedence. Sum the points for supported claims, once per claim. A score of 60% means the evaluator verified 60 of 100 rubric points. A claim the evaluator did not detect earns no points on that attempt. If it finds no reliable evidence, sees a material conflict, or receives invalid output, show a clarification or retry state without a percentage. Valid JSON alone cannot establish the correctness of the evidence. [Short-answer grading benchmark](https://aclanthology.org/S13-2045/) · [Partial-credit study](https://aclanthology.org/2026.bea-1.29/)
4. **Select GM feedback.** Use the authored decision table for low, partial, near-complete, and full credit, plus separate misconception and clarification responses. On the Rust borrowing question, explaining last use and why the borrows overlap earns 60 points. In Guided Mode the GM can reply, “You got the first two ideas. Want a hint about preallocation, or to see my answer?” The renderer displays approved text. Model output is never treated as a tool request, command, solution, or game reward.

The preview uses **Qwen3-0.6B Q8_0** and `llama-completion` in CPU mode. The publisher lists **639 MB on disk**. The staging script pins the model and executable hashes and packages one model. The current adapter starts a fresh bounded process for each assessment and passes the CLI's offline flag. It rejects excessive input, limits context, threads, generation and output, and checks that proposed evidence refers to the submitted answer. The release gate still requires broader paraphrase and misconception testing, whole-app memory measurements, and worker isolation checks. [Pinned model artifact](https://huggingface.co/Qwen/Qwen3-0.6B-GGUF/blob/main/Qwen3-0.6B-Q8_0.gguf) · [Prompt injection guidance](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)

## Architecture and offline runners

Build the interface in React, TypeScript, and Vite. Electron packages the UI and launches the existing Node engine in a utility process. Retain the book assets, Canvas creature renderer, content models, and SQLite store. Serve the app on a private loopback port with a per-launch secret, host and origin validation, and a dedicated Electron session. Sandbox the renderer, disable Node integration, restrict navigation, and expose only narrowly validated native operations. [Electron security](https://www.electronjs.org/docs/latest/tutorial/security) · [Electron utility process](https://www.electronjs.org/docs/latest/api/utility-process)

The engine authenticates the hero and challenge, owns scheduling and rewards, and gives a Windows broker a bounded grading request. The broker launches compiler, execution, and inference workers in separately restricted Windows AppContainers and Job Objects. Compiler sandboxes matter because source can read files during compilation. Allow only known binaries, necessary runtime files, bounded scratch space, and private pipes. Deny network, arbitrary paths and child launches, inherited secrets, and access to saves. Permit only the necessary confined compiler/linker process trees. Keep runner limits for time, memory, output, and disk. On a failed sandbox setup, refuse that execution. [Windows AppContainer](https://learn.microsoft.com/windows/win32/secauthz/implementing-an-appcontainer) · [Windows Job Objects](https://learn.microsoft.com/windows/win32/procthread/job-objects)

| World | Packaged implementation and proof needed |
| --- | --- |
| JavaScript | Embed QuickJS in a restricted worker. Each case gets a fresh context and bounded promise-job processing. Use authored host fixtures for API behaviors the book needs and keep the JavaScript language contract explicit. Test ECMAScript, callback, and microtask parity for the published exercises. [QuickJS memory and interruption](https://bellard.org/quickjs/quickjs.html#Memory-handling) · [Node VM security boundary](https://nodejs.org/api/vm.html) |
| TypeScript | Run the pinned TypeScript compiler in strict mode against a virtual set of bundled standard libraries and authored type fixtures. Require successful type checks before emitting executable JavaScript. Run the result in the JavaScript worker. Include positive and negative type assertions to catch unsafe widening. Test behavioral constraints separately. [Compiler API](https://github.com/microsoft/TypeScript/wiki/Using-the-Compiler-API) · [No emit on error](https://www.typescriptlang.org/tsconfig/noEmitOnError.html) |
| Rust | Bundle the pinned compiler, linker, and WASI standard library. Compile to `wasm32-wasip1` and run in Wasmtime. Keep all 14 current exercises graded. The installed Level 20 case checks bounded admission and permit ownership across deterministic interleavings. Native CI keeps the real-thread check. [Rust grader design](STANDALONE-RUST-GRADER-DESIGN.md) |
| Go | Bundle pinned standard Go tools and libraries. Build pure Go for `wasip1/wasm` with toolchain and dependency downloads disabled. A trusted reactor export lets the worker call a named case and observe its return. Fixtures join or cancel goroutines before returning. Validate channels, contexts and bounded concurrency. WASI execution does not measure native Go parallelism. [Go WASI support](https://go.dev/blog/wasi) · [Go reactor exports](https://go.dev/blog/wasmexport) |

Keep successful results tied to the expected suite, source revision, attempt ID, and mode. The worker must report a complete result through its protocol. Guest stdout and process exit code cannot independently award a pass. Use one queue for heavy compiler and model work. Keep the UI responsive and expose queued and cancel states. Evict an idle model before a compile when the memory budget requires it. Track limits per worker and admit work only when the measured app budget allows it.

### Engine contracts

| Operation | Request and result |
| --- | --- |
| Start or resume encounter | Resolve the active hero and challenge from local state. Load the saved mode, revision, draft, and aid history. Issue an attempt ID. |
| Create Workbench run | Accept the attempt ID, source and draft revision, run purpose, and bounded custom input for practice. Resolve the suite and difficulty in the engine. Return a run ID. |
| Read or cancel run | Return progress only to its owning hero and attempt. Cancel queued or running work by ID. The final result includes verdict, permitted case information, timings, and whether a new clear was saved. |
| Assess written answer | Accept the prompt, response, and draft revision. Save the answer and validated assessment for the same revision. Return rubric points and an approved feedback ID, or an unscored status. |
| Reveal aid or answer | Recheck the active mode in the engine, record aid disclosure where applicable, and return the authored text. A cached or delayed reply must pass the same access rules. |

## Saves, upgrades, and package

- Keep one database per world under a stable Electron `userData` path. Store versioned challenge attempts and clears, aid disclosure, and written assessments separately from the existing Boolean choice result. Save drafts, timestamps, and revisions so a late result cannot attach to a different hero or edited submission. Preserve prior Forge marks and prevent duplicate XP during migration and retries.
- Import the four existing SQLite files with the SQLite backup API so committed WAL records come across. Preview the source and destination, validate before activation, and keep the source as a recovery copy. Leave occupied worlds to an explicit restore flow. Offer a browser export for drafts or positions that never reached SQLite. Test interruption and restore across both formats. [Existing save layout](../server.mjs) · [SQLite backup API](https://nodejs.org/download/release/latest-v24.x/docs/api/sqlite.html#sqlitebackupsource-db-path-options)
- Use Electron Forge with Squirrel.Windows to produce the signed and timestamped setup. Include checksums, component hashes, release notes, licenses and software bill of materials. Handle installer events before starting the engine. Upgrade and repair through the setup file, and preserve saves on uninstall and reinstall by default. Measure the new installer size with all runtimes and the model. The earlier Rust-only size estimate does not cover this package. [Windows installer](https://www.electronforge.io/config/makers/squirrel.windows)

## Tests and release gates

Keep the existing `npm test`, `npm run test:browser`, `npm run test:book`, and `python verify-worlds.py` checks. Add required Windows package tests for all four runtimes and the local GM. A skipped backend is a release failure. [Current CI](../.github/workflows/verify.yml)

| Test area | Required evidence |
| --- | --- |
| App and game flow | Create and resume heroes across worlds. Check paths, A/D focus behavior, drafts, GM panels, character sheet, native exports, keyboard and screen reader status, and reduced motion. Replay both special encounters. Exercise back/forward, hero changes, and restart while an answer or run is pending. |
| Every published code suite | The reference passes every case. The starter and representative wrong solutions fail the intended checks. Detect hardcoded samples, type errors, bad async ordering, aliasing, invalid inputs, and time or memory overruns where relevant. Run cases repeatedly with fixed inputs. Require a public example and sealed coverage for every graded encounter. |
| Victory and persistence | A sample pass, a text score, partial passes, failed or canceled runs, and malformed worker results leave the creature standing. A verified full submit persists the clear and awards eligible XP exactly once, including on retry and across a crash. Old saved clears survive upgrade. |
| Diamond Goblin | The diamond can appear anywhere on the book page without blocking links. An active fight survives page turns and reloads. Verify code and choice in order, no HP loss for examples or outages, and one loot bag per hero and world. |
| Hard Mode | Attempt aid access through the UI, editor, direct API, cached responses, restart, and hero switch. Block assistance in Hard. Keep diagnostics and scoring. Check aid disclosure and badge eligibility after switching modes or repeating a challenge. |
| GM answer quality | Have two reviewers label roughly 400 pilot responses, including a held-out set of at least 150 critical negatives. Keep paraphrase families together. Compare authored rules alone with the candidate model plus validated rubric scoring. Test partial answers, valid alternatives, negation, false reasoning, ambiguous phrasing, and prompt injection. Initial gates are at least 95% awarded-claim precision, at least 75% scoring coverage for in-scope responses, at most 10 percentage points mean absolute error on scored answers, and zero high-credit verdicts on that critical set. Report counts and per-world results. Test invalid model output and timeout without a fabricated score. |
| Runtime isolation | Attempt reads of saves and credentials, outbound and loopback network access, arbitrary child launches, sealed-case disclosure, forged output, and resource floods. Check cleanup after cancellation and forced shutdown. Test Windows restrictions with networking enabled as well as offline. |
| Packaged release | On clean Windows 11 Home and Pro x64 VMs, disconnect before installation. Launch without admin, grade a solution in each world, score written text, and upgrade and repair using only the signed installer. Confirm all assets, save recovery, first-run response, and zero game egress in a separate connected trace. |

On a 4 GB Windows 11 x64 VM with two vCPUs and SSD-backed storage, measure the time-aligned total working set across app processes and workers. Include resident model mappings, which a private-memory-only measure can miss. Report private commit and worker peaks separately. Target a peak under **2,000,000,000 bytes** for normal play with alternating code and written submissions. Proposed latency targets are a world picker within 5 seconds on cold launch, p95 under 6 seconds for warm written evaluations and under 12 seconds for the first cold evaluation. Measure compile and case times per language against representative suites. Adjust model, runtime, or scheduling based on measurements before releasing. [Windows process memory counters](https://learn.microsoft.com/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex2)

## Build sequence

1. **Prove the constraints.** Package a minimal Electron build with SQLite and one graded exercise per world. Confirm the Windows sandbox, two-stage Rust and Go builds, JS runtime parity, TypeScript checks, and a real CPU model run. Run on the lowest supported machine and choose the model based on memory, latency, and labeled scoring quality.
2. **Build one complete dungeon.** Connect the React reader, hero saves, GM panels, and Code Workbench to one working encounter per world. Exercise the full example, submit, save, and defeat loop. Add Hard Mode and authored hints, then verify mode and reward rules through the local engine.
3. **Migrate content and saves.** Convert the catalog and cover every published challenge. Regenerate book instructions. Validate legacy hero import and browser drafts. Run the written-rubric pilot and enable scoring only for reviewed prompts.
4. **Release the standalone app.** Sign the setup, run the entire acceptance matrix, and publish the installer with checksum and release notes. Completion requires working offline code and written grading, Hard Mode, durable victory, and the measured app budget on the supported Windows machines.
