# Chapter 26 Cancellation Is Destruction at a Boundary

An async operation can stop being polled because its owner drops it. A timeout, a losing branch in a race, a disconnected caller, or service shutdown can all lead to that event. The future's stored values are then destroyed, but statements that would have run after the current suspension point do not run. Cancellation therefore connects control flow directly to ownership and destruction.

The difficult question is what has already happened. Dropping a future can release a local reservation, but it cannot erase a packet already sent or a database commit already accepted. A good cancellation contract identifies the boundary between reversible local preparation and externally visible effects. It also defines what the caller may conclude when that boundary was crossed but no result was received.

## Cleanup Must Exist in Stored State

Consider code that acquires a permit, awaits work, and then explicitly returns the permit. If the future is dropped during the await, the final return statement is skipped. Resource release must instead be represented by an owned guard whose destructor runs when suspended state is destroyed.

This complete program reserves capacity and then suspends forever. Dropping the future restores capacity through the guard.

```rust
use std::cell::Cell;
use std::future::{self, Future};
use std::rc::Rc;
use std::task::{Context, Poll, Waker};

struct Pool {
    free: Rc<Cell<usize>>,
}

struct Permit {
    free: Rc<Cell<usize>>,
}

impl Pool {
    fn take(&self) -> Option<Permit> {
        let available = self.free.get();
        if available == 0 {
            return None;
        }
        self.free.set(available - 1);
        Some(Permit { free: Rc::clone(&self.free) })
    }
}

impl Drop for Permit {
    fn drop(&mut self) {
        self.free.set(self.free.get() + 1);
    }
}

async fn hold(pool: &Pool) {
    let _permit = pool.take().expect("capacity available");
    future::pending::<()>().await;
}

fn main() {
    let pool = Pool { free: Rc::new(Cell::new(1)) };
    let mut operation = Box::pin(hold(&pool));
    assert_eq!(pool.free.get(), 1);
    let mut context = Context::from_waker(Waker::noop());
    assert_eq!(operation.as_mut().poll(&mut context), Poll::Pending);
    assert_eq!(pool.free.get(), 0);
    drop(operation);
    assert_eq!(pool.free.get(), 1);
}
```

Before polling, the body has not acquired a permit. After the first poll, the guard is retained in suspended state. Dropping the boxed future destroys that state and returns the permit. The example uses `Rc<Cell<_>>` because all operations occur on one thread; a concurrent pool would use a synchronization design appropriate to its accounting.

The destructor must remain simple and reliable. It cannot perform an ordinary async wait, and panicking during cleanup can create additional failure paths. Returning an in memory permit is a good fit. Completing a remote rollback that may block indefinitely is not. Ownership based cleanup solves resource lifetime locally; it does not turn a network protocol into a synchronous destructor.

## Cancellation Safety Is Operation Specific

One useful question is whether dropping and recreating an operation loses progress or changes meaning. A receive future may be designed so that cancellation before completion leaves the next message available. A multi step parser may instead consume some bytes into its own temporary buffer and lose them when dropped. Both can be memory safe, yet only one is restartable under that particular calling pattern.

The answer depends on where partial progress lives. If consumed bytes live in a connection object's persistent buffer, cancelling one read attempt can leave the connection ready for the next attempt. If they live only inside the future, destruction may discard them. Designing persistent state outside the cancellable operation can make retries safe, at the cost of a more explicit state machine.

A write operation has a different problem: some prefix may already have reached the peer. Restarting the whole write can duplicate bytes. Even when an API documents that a particular primitive is cancellation safe, a larger composition may not be. A sequence of individually restartable steps can still have an externally visible effect between them.

Read cancellation documentation at the granularity of the actual operation. A runtime's selection macro can describe how branches are dropped, but it cannot promise that every arbitrary future placed in a branch is safe to abandon. The future's own resource protocol supplies that part of the contract.

## Separate Preparation From Commit

A useful design makes preparation an owned value and commit an explicit transition. Preparation can allocate buffers, validate input, and reserve local capacity. Commit then transfers the prepared value into the authoritative owner. Whether commit itself can suspend is an important API choice.

The following library example keeps the domain transition synchronous. It is a small model of a larger design, not a claim that durable storage can always commit without waiting.

```rust
#[derive(Debug, PartialEq)]
struct Receipt {
    index: usize,
}

struct Prepared {
    record: String,
}

struct Ledger {
    records: Vec<String>,
}

impl Prepared {
    fn validate(record: String) -> Result<Self, &'static str> {
        if record.trim().is_empty() {
            return Err("empty record");
        }
        Ok(Self { record })
    }

    fn commit(self, ledger: &mut Ledger) -> Receipt {
        let index = ledger.records.len();
        ledger.records.push(self.record);
        Receipt { index }
    }
}

async fn prepare(record: String) -> Result<Prepared, &'static str> {
    std::future::ready(()).await;
    Prepared::validate(record)
}
```

Dropping `Prepared` before commit discards an uncommitted local record. Once `commit` returns, the record belongs to the ledger. There is no await inside the state transition, so task cancellation cannot intervene through an async suspension in the middle of this function. Ordinary panics and allocation failures still require their own analysis; absence of await is not a universal transaction guarantee.

For a remote system, commit usually involves uncertainty. The server can accept a request while the client times out before receiving a reply. A stable operation identifier lets the client query or retry without inventing a second operation. The durable authority must define deduplication and retention, because a local cancellation guard cannot know the remote outcome.

## Timeouts Bound Waiting Under Assumptions

A timeout commonly races an operation against a timer. If the timer wins, the wrapper drops or stops polling the operation and returns a timeout result. This bounds the caller's wait only if the executor can poll the timer and the operation yields control. A blocking poll or long synchronous computation can prevent the timeout branch from running promptly.

A timeout also does not necessarily stop independently spawned work. A future awaiting a worker's reply may be dropped while the worker continues. The result receiver disappears, but the job's owner is elsewhere. This can be correct if the service deliberately completes accepted work, or wasteful if the caller expected cancellation to propagate.

Define cancellation propagation explicitly. Does dropping a request signal the worker? Does the worker check that signal between stages? Can the worker stop after an external effect begins? Does it still record the final outcome for later lookup? These are protocol questions that cannot be answered solely by the lifetime of a local future.

Deadlines often compose better than repeated relative timeouts. Passing one absolute deadline through several layers prevents each layer from consuming the full budget independently. The clock and deadline representation should match the runtime's timer system. Retries should consume the same overall budget unless the API intentionally grants a new one.

## Cooperative Cancellation Has Checkpoints

An independent worker can observe a cancellation token. The token asks the worker to stop; it does not preempt arbitrary instructions. The worker chooses safe checkpoints at which its invariants permit exit.

This complete threaded example makes that distinction visible without an async runtime.

```rust
use std::sync::Arc;
use std::sync::atomic::{AtomicBool, Ordering};
use std::thread;

struct CancelOnDrop(Arc<AtomicBool>);

impl Drop for CancelOnDrop {
    fn drop(&mut self) {
        self.0.store(true, Ordering::Release);
    }
}

fn main() {
    let cancelled = Arc::new(AtomicBool::new(false));
    let owner = CancelOnDrop(Arc::clone(&cancelled));
    let worker = thread::spawn(move || {
        let mut batches = 0_u64;
        while !cancelled.load(Ordering::Acquire) {
            batches = batches.wrapping_add(1);
            thread::yield_now();
        }
        batches
    });
    drop(owner);
    let _completed_batches = worker.join().unwrap();
}
```

The worker may perform zero or many batches before observing cancellation. Joining establishes that it actually stopped. Dropping the guard alone only changes the flag. A real worker should place checkpoints between bounded units of work and define which partial results are retained or discarded.

If a checkpoint occurs while a local invariant is temporarily broken, stopping there can expose damaged state. A good decomposition makes each unit complete a coherent transition before checking cancellation again. Long blocking calls may not offer such checkpoints, so cancellation latency includes their duration unless the underlying API provides its own interruption mechanism.

## Dropping a Handle and Stopping Work Differ

A task handle is an ownership relationship with runtime specific semantics. Dropping it might detach the task, request cancellation, or perform some other documented action. Never infer the behavior from the generic word handle. Likewise, requesting an abort may require later scheduling before the task's future is actually destroyed.

The distinction matters during shutdown. A service that drops every handle may leave background work alive. A service that requests cancellation but never waits may exit before cleanup finishes. A structured owner should retain the capabilities needed to observe termination, collect failures, and release resources in a defined order.

Cancellation can also race with completion. A caller may receive a cancellation result even though an effect completed just before the signal was processed. The API should avoid promising that cancellation means nothing happened unless it has a protocol that truly establishes that fact. Often the honest result is that the caller stopped waiting and must consult an operation identifier for the final outcome.

## Design Around Observable Outcomes

Write a cancellation table for each meaningful phase: not started, locally prepared, submitted externally, committed, and acknowledged. For each phase, state who owns resources, what dropping the future does, and what the caller can safely retry. This table is an engineering tool rather than a public ritual; it exposes missing cases before they become production incidents.

Keep local cleanup and domain compensation distinct. Releasing a buffer is cleanup. Sending a reversing transaction is a new domain operation that can fail independently and may need an audit trail. A destructor should not silently pretend that compensation restores history.

When cancellation cannot safely interrupt an operation, isolate that operation behind an owner that continues to completion and records the result. The caller can abandon its wait while the owner preserves consistency. This can increase background work, so admission control must account for accepted operations that no longer have waiting callers.

## Exercises

1. A future takes a permit, awaits a network response, and returns the permit with an explicit final statement. Explain the cancellation leak and redesign ownership.

2. A timeout returns an error while a charge request may already have reached a server. State what the timeout proves and what additional protocol is needed for a safe retry.

3. A worker checks a cancellation flag after removing an item from a queue but before recording where it will go. Explain the state loss risk and propose a checkpoint boundary.

## Reasoned Solutions

1. Dropping suspended state skips the final statement. Store an owned permit guard across the await and release capacity in its destructor. Ensure the destructor performs bounded local cleanup and cannot require an async wait. If release itself is remote, an owning service must manage that protocol separately.

2. The caller's waiting policy expired; the remote effect may be absent, in progress, or committed. Use a stable operation identifier and an authoritative deduplication or status lookup protocol. Retrying the same logical operation must not create a new charge merely because the previous acknowledgement was lost.

3. The item has left durable or persistent queue state but has not entered another accounted ownership state. Cancellation can make it disappear from the intended workflow. Retain it in an owned in flight record with a defined drop policy, or check cancellation before removal and again only after a coherent handoff. The correct boundary is where every item still has an accountable owner.
